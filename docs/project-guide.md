# 1. โปรเจกต์นี้คืออะไร

ลองนึกว่าระบบนี้คือ **พนักงานขายในร้าน 1 คน** ชื่อ "น้องช้อป" ที่ทำงาน 5 อย่างต่อการคุย 1 รอบ:

| # | พนักงานทำอะไร | ไฟล์โค้ด |
|---|---|---|
| 1 | **จดโน้ต** ว่าลูกค้าอยากได้อะไร | `src/memory.py` |
| 2 | **คิดในใจ** ว่าควรถามต่อ หรือไปหยิบของเลย | `src/planner.py` |
| 3 | **เดินไปหาของ** ในคลังสินค้า | `src/retriever.py` |
| 4 | **คัดของที่ดีที่สุด 3 ชิ้น** ออกมา | `src/reranker.py` |
| 5 | **เล่าให้ลูกค้าฟัง** ว่าทำไมแนะนำ 3 ชิ้นนี้ | `src/agent.py` |

ทั้ง 5 อย่างประกอบกันในไฟล์ `src/agent.py` (ตัวคุมงาน)

**โปรเจกต์นี้รวม 3 แนวคิดใหญ่:**

| แนวคิด | แปลว่าอะไรแบบบ้านๆ |
|---|---|
| **AI Agent** | ระบบ "คิดก่อนตอบ" ว่าจะถาม/แนะนำ/คุย ไม่ใช่ตอบมั่วๆ |
| **CRS** (ระบบแนะนำแบบสนทนา) | จำสิ่งที่ลูกค้าบอกไว้เรื่อยๆ เปลี่ยนใจ/ปฏิเสธได้ |
| **RAG** | แนะนำจากสินค้าจริงในคลังเท่านั้น ไม่แต่งสินค้าปลอมขึ้นมา |

**เครื่องมือที่ใช้ (ฟรีทั้งหมด รันในเครื่อง):**
- **Typhoon2** = โมเดล AI ภาษาไทย (ตัวที่คิดและเขียนคำตอบ)
- **bge-m3** = ตัวแปลงข้อความเป็นตัวเลข (ไว้ค้นหา)
- **ChromaDB** = ที่เก็บสินค้าไว้ค้นหาเร็วๆ
- **ข้อมูล** = สินค้าจริง 600 ชิ้น 6 หมวด จาก Amazon Reviews 2023

# 2. ศัพท์ที่ต้องรู้ก่อน

- **LLM / โมเดล AI** = โปรแกรม AI ที่อ่าน/เขียนภาษาคนได้ (ในที่นี้คือ Typhoon2)
- **prompt** = ข้อความคำสั่งที่เราส่งให้ AI
- **system prompt** = คำสั่งบอก "บทบาท/กติกา" ให้ AI ก่อนเริ่มงาน เช่น "คุณเป็นพนักงานขาย ตอบสั้นๆ"
- **JSON** = รูปแบบข้อมูลที่มีช่องชัดเจน เช่น `{"หมวด": "หูฟัง", "งบ": 40}`
- **embed / เวกเตอร์** = แปลงข้อความเป็น **ชุดตัวเลข** เพื่อให้คอมพิวเตอร์วัดว่า 2 ข้อความ "ความหมายใกล้กันแค่ไหน" (เช่น "หูฟัง" กับ "earphone" ได้ตัวเลขใกล้กัน)
- **vector database (ChromaDB)** = สมุดเก็บชุดตัวเลขพวกนี้ และค้น "ของที่ความหมายใกล้กันที่สุด" ได้เร็ว

# 3. เตรียมของก่อนเปิดร้าน (`catalog.py`)

ทำ **ครั้งเดียว** ตอนเปิดโปรแกรม — เอาสินค้า 600 ชิ้นเข้า "สมุดค้นหา" (ChromaDB)

**ขั้น 1 — แปลงสินค้าแต่ละชิ้นเป็นข้อความก้อนเดียว** (`build_document`)
```python
parts = [p["title"], f"หมวด: {p['category']}"]
if p.get("brand"):    parts.append(f"แบรนด์: {p['brand']}")
parts.append(f"ราคา: {p['price']} ดอลลาร์")
if p.get("features"): parts.append(f"จุดเด่น: {', '.join(p['features'])}")
```
👉 รวม ชื่อ+หมวด+แบรนด์+ราคา+จุดเด่น+รายละเอียด เป็นข้อความเดียว เพราะลูกค้าอาจถามด้วยอะไรก็ได้ ใส่ครบ AI จะจับได้ทุกทาง

**ขั้น 2 — แปลงเป็นตัวเลขแล้วเก็บ** (`build_index`)
```python
batch = 64                                   # ทำทีละ 64 ชิ้น
for i in range(0, len(products), batch):
    chunk = products[i:i + batch]
    vectors = llm.embed([build_document(p) for p in chunk])  # ข้อความ → ตัวเลข
    col.add(ids=..., embeddings=vectors, metadatas=[{
        "price": float(p["price"]),                  # เก็บราคาแยกไว้ "กรอง"
        "json": json.dumps(p, ensure_ascii=False),   # เก็บข้อมูลเต็มไว้ "ดึงกลับ"
    } ...])
```
👉 2 จุดสำคัญ:
- **ทำไมทีละ 64?** เคยลองยัด 600 ชิ้นทีเดียว → ตัวแปลงตัวเลข (bge-m3) **ล่ม** เลยแบ่งเป็นก้อนเล็ก
- **เก็บ 2 อย่างคู่กัน:** (ก) ราคาแยกเป็นตัวเลข ไว้ "กรอง" ทีหลัง (ข) ข้อมูลสินค้าเต็มยัดเป็นข้อความ JSON ไว้ "ดึงกลับมาใช้" เพราะ ChromaDB เก็บข้อมูลซับซ้อนไม่ได้ เก็บได้แค่ค่าเดี่ยวๆ

# 4. เดินตามลูกค้า 1 คน — 5 ขั้น

**ลูกค้าพิมพ์:** *"หาหูฟังไร้สายไว้ออกกำลังกาย งบไม่เกิน 40"*

ตัวคุมงานอยู่ที่ `agent.py` ฟังก์ชัน `respond()` — เรียก 5 ขั้นตามลำดับ

## ① จดโน้ต — `memory.py`

**เปรียบเทียบ:** พนักงานฟังลูกค้าแล้วจดใส่กระดาษที่มี **ช่องตายตัว** (จะจดมั่วนอกช่องไม่ได้)

ช่องที่จด (เรียกว่า `profile`) มี 8 ช่อง:
```python
EMPTY_PROFILE = {
    "category": "",          # หมวด เช่น "หูฟัง"
    "budget_max": None,      # งบ (ตัวเลข)
    "brands_liked": [],      # แบรนด์ที่ชอบ
    "brands_disliked": [],   # แบรนด์ที่ไม่เอา
    "features_wanted": [],   # ฟีเจอร์ เช่น ["ไร้สาย"]
    "use_case": "",          # เอาไปทำอะไร
    "rejected_titles": [],   # ของที่ปฏิเสธไปแล้ว (ห้ามเสนอซ้ำ)
    "other_preferences": "", # อื่นๆ
}
```

**วิธีจด:** เอาโน้ตเดิม + ข้อความใหม่ ส่งให้ AI ช่วยเติมช่อง แล้ว AI ตอบกลับเป็น JSON:
```json
{"category": "หูฟังไร้สาย", "budget_max": 40,
 "features_wanted": ["ไร้สาย", "กันเหงื่อ"], "use_case": "ออกกำลังกาย", ...}
```

**โค้ดสำคัญที่สุด** — เราไม่เชื่อ AI ทันที ต้องกรองก่อนจด:
```python
for key, default in EMPTY_PROFILE.items():   # วนช่องที่ "เรารู้จัก" ทีละช่อง
    if key not in result:
        continue                              # AI ไม่ตอบช่องนี้ → เก็บค่าเดิมไว้
    val = result[key]
    if key == "budget_max":
        if isinstance(val, (int, float)):     # งบต้องเป็นตัวเลขเท่านั้น
            self.profile[key] = val
    elif isinstance(val, type(default)):      # ช่องอื่น: ชนิดข้อมูลต้องตรง
        self.profile[key] = val
```
👉 เราวน **ช่องที่เรากำหนดไว้** (8 ช่อง) ไม่ใช่วนสิ่งที่ AI ตอบ → ถ้า AI แถมช่องแปลกๆ มา มัน **หลุดเข้าโน้ตไม่ได้เลย**
👉 **งบมีกฎพิเศษ:** รับเฉพาะตัวเลข เพราะเคยเจอบั๊ก — พอลูกค้าพิมพ์รอบต่อไปที่ไม่พูดเรื่องงบ AI ชอบส่ง `null` มาทับ ทำให้งบเดิมหาย เลยล็อกไว้ว่ารับเฉพาะตัวเลข

## ② คิดในใจว่าจะทำอะไร — `planner.py`

พนักงานคิดว่า "ข้อมูลพอหยิบของหรือยัง?" แล้วเลือก 1 ใน 3 ทาง:

| เลือก | แปลว่า | เมื่อไหร่ |
|---|---|---|
| `ask` | ถามเพิ่ม | ยังไม่รู้อะไรเลย |
| `recommend` | ไปหยิบของมาแนะนำ | รู้พอแล้ว (หมวดหรือการใช้งานอย่างน้อย 1 อย่าง) |
| `chat` | คุยเล่น/ตอบคำถาม | ทักทาย หรือถามข้อมูลเฉยๆ |

**โค้ดแผนสำรอง** (เผื่อ AI ตอบมั่ว):
```python
action = result.get("action", "")
if action not in ("ask", "recommend", "chat"):   # ตอบเป็นคำนอก 3 คำนี้ = เพี้ยน
    has_pref = bool(profile["category"] or profile["use_case"] or ...)
    action = "recommend" if has_pref else "ask"  # ถ้าโน้ตมีข้อมูล → หยิบของเลย

if action == "ask" and ask_count >= 2:           # ถามเกิน 2 ครั้ง
    action = "recommend"                          # → บังคับหยิบของ (กันถามวนไม่จบ)
```
👉 ถ้า AI ตอบแปลกๆ เรามีกฎสำรองตายตัว (ดูว่าโน้ตมีข้อมูลไหม) เพื่อให้ระบบเดินต่อได้เสมอ + ถามได้มากสุด 2 ครั้ง

## ③ เดินไปหาของในคลัง — `retriever.py`

**ขั้น 3.1 ประกอบประโยคค้นหา** (`build_query`):
```python
parts = [user_message]                                    # ข้อความล่าสุด
if profile.get("category"):  parts.append("หมวด: " + profile["category"])
if profile.get("use_case"):  parts.append("ใช้สำหรับ: " + profile["use_case"])
if profile.get("features_wanted"): parts.append("ฟีเจอร์ที่อยากได้: " + ...)
```
👉 เราไม่ค้นด้วย **ข้อความล่าสุดอย่างเดียว** แต่เอา **โน้ตทั้งหมดมารวม** เหตุผล: ถ้ารอบต่อไปลูกค้าพิมพ์แค่ "เอาสีดำ" เราต้องยังจำได้ว่ากำลังหา **หูฟัง** อยู่

**ขั้น 3.2 ค้นจริง + กรองราคา** (`retrieve`):
```python
vec = llm.embed([query])[0]                                          # ประโยค → ตัวเลข
where = {"price": {"$lte": float(budget_max)}} if budget_max else None  # กรองราคา
res = col.query(query_embeddings=[vec], n_results=n, where=where)
```
👉 2 อย่างเกิดพร้อมกัน:
- **ค้นด้วยความหมาย:** แปลงประโยคเป็นตัวเลข แล้วให้ ChromaDB หาสินค้าที่ตัวเลขใกล้กันที่สุด
- **กรองราคาแบบเป๊ะ:** `$lte` = "น้อยกว่าหรือเท่ากับ" → เอาเฉพาะราคา ≤ 40 · งบเป็นตัวเลข ต้องกรองเป๊ะ 100% ไม่ใช่หวังให้ AI เดา (จุดเด่นเชิงพาณิชย์)

จากนั้นตัดของที่ลูกค้าเคยปฏิเสธออก แล้วได้ **ผู้เข้าชิง 10 ชิ้น**

## ④ คัดของที่ดีที่สุด 3 ชิ้น — `reranker.py`

**ค้นเจอแล้ว ทำไมต้องคัดอีก?** เพราะการค้นด้วยตัวเลขดูแค่ "ความหมายคล้าย" — บางชิ้นชื่อคล้ายคำว่า "หูฟัง" มากแต่จริงๆ **แพงเกินงบ** หรือเป็น **แบรนด์ที่ไม่ชอบ** เราเลยให้ AI มาตรวจซ้ำ

**วิธี:** เอาผู้เข้าชิง 10 ชิ้นมาให้ AI **ให้คะแนน 0-10 ทีละชิ้น** เทียบกับโน้ต (เกินงบ = คะแนนต่ำมาก, ของที่ปฏิเสธ = ให้ 0)

```python
ranked = sorted(candidates, key=lambda m: m["fit_score"], reverse=True)  # เรียงคะแนนมาก→น้อย
ranked = [m for m in ranked if m["fit_score"] >= 3] or ranked[:1]        # ตัดคะแนนต่ำ<3 ทิ้ง
return ranked[:top_n]                                                     # เอา 3 อันดับแรก
```
👉 `... or ranked[:1]` = ถ้ากรองแล้วเหลือ 0 ชิ้น (ทุกชิ้นแย่หมด) จะบังคับคืนอย่างน้อย 1 ชิ้น ไม่ให้หน้าจอว่าง
👉 **แผนสำรอง:** ถ้า AI ให้คะแนนไม่ได้เลย → ใช้ลำดับการค้นเดิม (ระบบไม่ล่มกลางคัน)

## ⑤ เล่าให้ลูกค้าฟัง — `agent.py`

เอา 3 ชิ้นที่คัดได้มาเขียนเป็น "ข้อมูลจริง" ส่งให้ AI พร้อมกำชับเข้ม:
```python
context = "\n\n".join(f"ชิ้นที่ {i+1}: {m['title']}\nราคา ${m['price']} ..." for ...)
reply = llm.chat(..., system=RECOMMEND_SYSTEM)   # RECOMMEND_SYSTEM สั่ง: แนะนำจากรายการนี้เท่านั้น
```
โดย `RECOMMEND_SYSTEM` สั่งว่า: *"แนะนำจากรายการที่คัดมาแล้ว**เท่านั้น** ห้ามแนะนำนอกรายการ ห้ามพิมพ์ราคาผิด"*
👉 นี่คือ **หัวใจกันการมโน** — AI พูดได้แค่จากของจริง 3 ชิ้นที่เราหยิบมาให้ สร้างสินค้าปลอมเองไม่ได้

## 🎬 ตัวคุมงานเบื้องหลัง — `agent.py` ร้อย 5 ขั้นยังไง

5 ขั้นข้างบนไม่ได้ทำงานเอง — มี **ตัวคุมงาน (orchestrator)** คือคลาส `ProductRecAgent` ใน `agent.py` เป็นคนสั่งว่าใครทำก่อนหลัง (เปรียบเหมือน **ผู้จัดการ** ที่ไม่ได้ลงมือค้น/คิดเอง แต่สั่งลูกทีมทำตามลำดับ)

**หัวใจคือฟังก์ชัน `respond()`** — ทำงาน 1 รอบต่อ 1 ข้อความลูกค้า:
```python
def respond(self, user_message):
    # [1] จดโน้ตก่อนเสมอ (ทุกข้อความ ไม่ว่าจะจบทางไหน)
    self.memory.update_profile(user_message, self.last_recommendations)
    # [2] ถามแผนจาก planner
    plan = planner.decide(self.memory.profile, self.memory.recent(),
                          user_message, self.ask_count)
    # [3-5] แตกเป็น 3 ทางตามแผน
    if plan["action"] == "recommend":
        reply, extra = self._recommend(user_message);  self.ask_count = 0
    elif plan["action"] == "ask":
        reply = self._ask(user_message);  self.ask_count += 1
    else:
        reply = self._chat(user_message)
    self.memory.add("user", user_message)          # บันทึกบทสนทนา
    self.memory.add("assistant", reply)
    return trace   # {reply, action, profile, picked, ...}
```

อ่านเป็นภาษาคน — ทำ 3 สเต็ป:
1. **จดโน้ตก่อนเสมอ** (เรียก memory)
2. **ถามแผน** (เรียก planner)
3. **แตกเป็น 3 ทาง** ตามที่ planner บอก:

| แผน | เรียกฟังก์ชันย่อย | ทำอะไร | จัดการ ask_count |
|---|---|---|---|
| recommend | `_recommend()` | ค้น→คัด→เขียน (ขั้น 3-4-5) | รีเซ็ตเป็น 0 |
| ask | `_ask()` | ถาม 1 คำถาม | +1 (กันถามวน) |
| chat | `_chat()` | ค้นเบาๆ + ตอบคุย | คงเดิม |

**2 ตัวจำที่ agent ถือไว้ข้ามรอบ:**
- **`ask_count`** — นับว่าถามไปกี่ครั้ง (พอถึง 2 planner จะบังคับ recommend)
- **`last_recommendations`** — ชื่อของที่เพิ่งแนะนำ ส่งให้ memory รอบถัดไปเพื่อเข้าใจว่า "ไม่เอาอันนี้" หมายถึงชิ้นไหน

**`trace`** = สมุดบันทึกทุกขั้นของรอบนี้ (action / โน้ต / ของที่คัด / คะแนน) — ส่งให้หน้าจอ (`--debug` หรือแผงข้างใน Streamlit) โชว์ "ความคิด" ของ agent → มีค่ามากตอนสอน

👉 สรุป: `agent.py` = **ผู้จัดการ** ที่สั่ง memory / planner / retriever / reranker + llm ให้ทำตามลำดับ แล้วรวมผลเป็นคำตอบเดียว (ต่างจาก `llm.py` ที่เป็นแค่ "สายโทรศัพท์" ไปหา AI — ดูหัวข้อถัดไป)

# 5. ตัวกลางคุยกับ AI — `llm.py`

ทุกไฟล์ข้างบน เวลาจะคุยกับ AI **ไม่คุยเอง** แต่เรียกผ่านไฟล์นี้ไฟล์เดียว (แก้ทีเดียว มีผลทั้งระบบ) มี 3 ฟังก์ชัน:

| ฟังก์ชัน | ทำอะไร | ใครใช้ |
|---|---|---|
| `chat()` | ถาม AI ให้ตอบเป็น **ข้อความคน** | ขั้น ⑤ |
| `chat_json()` | ถาม AI ให้ตอบเป็น **ช่องข้อมูล JSON** | ขั้น ①②④ |
| `embed()` | แปลง **ข้อความ → ตัวเลข** | ขั้น ③ |

**จุดสำคัญที่สุดของทั้งโปรเจกต์** อยู่ใน `chat_json`:
```python
try:
    data = json.loads(text)          # พยายามอ่านคำตอบ AI เป็น JSON
    if isinstance(data, dict):
        return data
except json.JSONDecodeError:
    pass
return {}                            # ถ้าอ่านไม่ได้ → คืน "ว่าง" ไม่ทำให้ระบบพัง
```
👉 AI ตัวเล็กตอบมั่วได้เสมอ บางทีตอบ JSON ที่พังอ่านไม่ได้ กฎของเราคือ **ถ้าพังก็คืนค่าว่าง ไม่ทำให้โปรแกรมหยุด** นี่คือเหตุผลที่ทุกขั้นต้องมี "แผนสำรอง"

# 6. 5 กลเม็ดที่ทำให้ระบบไม่พัง (ทั้งที่ใช้ AI ตัวเล็ก)

1. **ไม่เชื่อ AI 100%** — ทุกคำตอบตรวจก่อนใช้ และมีแผนสำรองตายตัวเสมอ
2. **โน้ตมีช่องตายตัว** — AI เติมข้อมูลนอก 8 ช่องที่กำหนดไม่ได้
3. **แยกวิธีกรอง 2 แบบ** — ราคา (ตัวเลข) กรองเป๊ะ / หมวด (ความหมาย) ใช้ค้นด้วยตัวเลข
4. **จำข้ามรอบ** — โน้ตอยู่ตลอดบทสนทนา ลูกค้าพูดต่อได้โดยไม่ต้องเริ่มใหม่
5. **เขียนให้อ่านง่าย** — ไม่ใช้ไลบรารีซับซ้อน เห็นทุกขั้นตอนชัด เหมาะเอาไปสอน

# 7. การวัดผล (Evaluation)

## ทำไมต้องวัด?
เหมือนร้านเปิดใหม่ เจ้าของบอกว่า "พนักงานฉันเก่ง" ไม่พอ — ต้องมี **ตัวเลขพิสูจน์** การวัดผลตอบ 3 คำถาม แยกเป็น 3 ไฟล์:

| คำถาม | ไฟล์ | วัดส่วนไหน |
|---|---|---|
| 1. ค้นของเจอตรงไหม? | `eval_products.py` | สมองส่วนค้นหา |
| 2. พฤติกรรมถูกไหม? | `test_dialogs.py` | ทั้งระบบรวมกัน |
| 3. เร็ว/เสถียรไหม? | `eval_system.py` | ความเร็ว + ความนิ่ง |
| 4. คุยแล้วปิดการขายได้ไหม? | `eval_simulator.py` | คุณภาพทั้งบทสนทนา |
| 5. ทายของชิ้นถัดไปจากประวัติจริงได้ไหม? | `eval_amazon_loo.py` | **ข้อมูลมาตรฐาน** (รีวิวจริง) |

## ศัพท์วัดผล (บ้านๆ)
- **Precision@10** = "ค้นมา 10 ชิ้น กี่ชิ้นที่ **ใช่**" — ใช่ 9 ชิ้น = 0.90
- **NDCG@10** = คล้าย Precision แต่ให้ความสำคัญกับ **ลำดับ** ด้วย (เอาของถูกไว้อันดับต้นๆ ได้คะแนนมากกว่า)
- **random baseline** = "ถ้าปิดตาหยิบมั่ว จะได้แค่ไหน" — ไว้เทียบว่าเราเก่งกว่ามั่วกี่เท่า
- **JSON failure rate** = "AI ตอบข้อมูลพังจนต้องใช้แผนสำรอง กี่ %" — ยิ่งต่ำยิ่งเสถียร

## ไฟล์ 1: `eval_products.py` — ค้นของเจอตรงไหม?

**มุมมองที่ 1 — ค้นตรงหมวดไหม:** เอาชื่อหมวด (เช่น "Office Products") ไปค้น แล้วดูว่า 10 ชิ้นที่ได้ เป็นของหมวดนั้นจริงกี่ชิ้น
```python
p10 = sum(1 for r in ranked[:10] if r in relevant) / 10   # นับชิ้นที่ "ใช่" ÷ 10
```

ผลจริง (label หมวดจาก Amazon ไม่ใช่เราตั้งเอง):

| หมวด | P@10 | NDCG@10 |
|---|---|---|
| Office Products | 1.00 | 1.00 |
| Sports and Outdoors | 1.00 | 1.00 |
| Cell Phones | 1.00 | 1.00 |
| Toys and Games | 0.90 | 0.94 |
| Home and Kitchen | 0.80 | 0.86 |
| Electronics | 0.70 | 0.76 |
| **เฉลี่ย** | **0.90** | **0.93** |

👉 ค้น 10 ชิ้น ถูกเฉลี่ย **9 ชิ้น** เทียบกับมั่ว (0.167) = **ดีกว่า 5.4 เท่า**
👉 จุดน่าสอน: Electronics ได้ต่ำสุด เพราะความหมาย **ทับ** กับ Cell Phones/Office → ค้นปนกันบ้าง ส่วนหมวดที่เอกลักษณ์ชัด (Office, Sports) ได้เต็ม

**มุมมองที่ 2 — กรองงบถูกไหม:** ค้นด้วยงบ เช่น $15 แล้วเช็คว่าทุกชิ้นราคา ≤ 15 จริงไหม

| ค้นด้วย | งบ | อยู่ในงบ | แพงสุดที่คืน |
|---|---|---|---|
| phone case cover | $15 | 10/10 | $13.99 |
| kitchen home gadget | $25 | 10/10 | $24.99 |
| sports fitness gear | $20 | 10/10 | $18.00 |

👉 **100% อยู่ในงบทุก query** — ยืนยันว่าการกรองราคาแบบเป๊ะทำงานสมบูรณ์

## ไฟล์ 2: `test_dialogs.py` — พฤติกรรมถูกไหม?

จำลอง **บทสนทนาจริง 5 สถานการณ์** แล้วเช็คว่าน้องช้อปทำตัวถูกไหม (แบบเดียวกับ unit test):

| # | สถานการณ์ | เช็คว่า |
|---|---|---|
| 1 | "หาเคสมือถือ งบไม่เกิน 15" | จับงบ=15 + แนะนำในงบ + มาจากคลังจริง |
| 2 | กำกวม → บอกชัด | พอบอกชัดถึงแนะนำ |
| 3 | ปฏิเสธชิ้นที่แนะนำ | ไม่เสนอชิ้นเดิมซ้ำ |
| 4 | "งบ 20" → "เพิ่มเป็น 50" | จำงบใหม่ได้ |
| 5 | "ร้านนี้ขายอะไรบ้าง" | เลือก chat (ไม่ยัดแนะนำ) |

```python
check("ทุกชิ้นอยู่ในงบ $15", all(m["price"] <= 15 for m in t["picked"]))  # ทุกชิ้น ≤ 15 ไหม
```
👉 **ผลจริง: ผ่าน ≈10/11 ข้อ** · ข้อที่พลาดคือบางครั้ง planner เลือก `ask` แทน `recommend` — ไม่ใช่บั๊ก แต่เป็นความไม่เสถียรของ LLM ตัวเล็ก (โค้ดเขียนหมายเหตุว่า "ลองรันซ้ำ")

## ไฟล์ 3: `eval_system.py` — เร็ว/เสถียรไหม?

**ผลจริง เวอร์ชันสินค้า (รัน 2026-07-28):**

| action | เวลา/turn | ทำไม |
|---|---|---|
| recommend | 17-25 วิ | เรียก AI 4 ครั้ง (จด→ตัดสิน→ให้คะแนน→เขียน) |
| ask / chat | 3.6-4.9 วิ | เรียก AI น้อยขั้นกว่า |
| **เฉลี่ย** | **~14 วิ/turn** | |

**JSON failure rate = 0%** (เรียก 12 ครั้ง พัง 0 ครั้ง) — AI ตอบข้อมูลในรูปแบบที่อ่านได้ทุกครั้ง ระบบนิ่งดี

แยกเวลาต่อชนิดการเรียก AI: `chat` เฉลี่ย 3.4 วิ · `chat_json` 4.0 วิ · `embed` 2.2 วิ

> **หมายเหตุตามตรง:** turn แรก (หูฟัง) วัดได้ 20.7 วิ สูงผิดปกติ เพราะ (ก) เป็นครั้งแรก โมเดลต้องโหลดเข้าการ์ดจอก่อน (cold start) และ (ข) รอบนั้น planner เลือก `ask` แทน `recommend` — ความไม่เสถียรของ LLM ตัวเล็กที่กล่าวไปแล้ว รันซ้ำตัวเลขจะนิ่งขึ้น

## ไฟล์ 4: `eval_simulator.py` — คุยหลายรอบแล้วปิดการขายได้ไหม?

**ต่างจาก 3 ไฟล์บนยังไง?** ไฟล์บนวัดทีละส่วน/ทีละข้อความ — ไฟล์นี้วัด **ทั้งบทสนทนาหลายรอบ** โดยให้ AI **อีกตัว** สวมบท "ลูกค้า" ที่มีสินค้าในใจ แล้วบรรยายความต้องการให้น้องช้อปเดา (ห้ามบอกชื่อ/แบรนด์ตรงๆ) — เหมือนมีลูกค้าปลอมมาลองคุยจริง

**วัด 3 อย่าง:**
- **Success@t** = คุยกันภายใน t รอบ น้องช้อปแนะนำของ *ตรงหมวด + อยู่ในงบ* ได้ไหม
- **Average Turns** = เฉลี่ยกี่รอบกว่าจะสำเร็จ (ยิ่งน้อย = ถามตรงจุด)
- **Exact-item hit** = เจอ *ชิ้นเป๊ะ* ที่ลูกค้าคิดไว้ไหม (โบนัส — ยากมากเพราะมีของคล้ายกันเยอะ)

**ผลจริง (ลอง 3 เป้าหมาย, สูงสุด 3 รอบ):**

| ตัวชี้วัด | ผล |
|---|---|
| Success@3 | **100%** (ปิดการขายได้ทุกครั้ง) |
| Success@1 | 66.7% (2 ใน 3 สำเร็จตั้งแต่รอบแรก) |
| Average Turns | **1.33 รอบ** |
| Exact-item hit | **0%** |

👉 อ่านผล: น้องช้อปแนะนำของถูกหมวด+ในงบได้ **ทุกบทสนทนา** เฉลี่ยแค่ ~1.3 รอบ (ถามตรงจุด) · แต่ **เจอชิ้นเป๊ะ 0%** เป็นผลซื่อสัตย์ — การเดา SKU เดียวเป๊ะจากคำบรรยาย ท่ามกลางสินค้าคล้ายกัน 600 ชิ้น ยากโดยธรรมชาติ (ระบบเก่งเรื่อง "หาของที่ตอบโจทย์" ไม่ใช่ "ทายใจว่าคิดถึงชิ้นไหนเป๊ะ")

> รันเต็ม: `python -m eval.eval_simulator 6 4` (6 เป้าหมาย, 4 รอบ) — ยิ่งเป้าเยอะยิ่งกินเวลา เพราะแต่ละรอบเรียก AI หลายครั้ง

## ไฟล์ 5: `eval_amazon_loo.py` — ทายของชิ้นถัดไปด้วยข้อมูลมาตรฐาน (รีวิวจริง)

**นี่คือ eval ที่ใช้ "ข้อมูลมาตรฐาน" เต็มตัว** — ตอบคำถามที่ว่า *"test_dialogs ทำด้วยข้อมูลมาตรฐานได้ไหม"* → ทำเป็น **ไฟล์แยกแบบนี้แทน** (test_dialogs วัดกฎ, ไฟล์นี้วัดความตรงใจด้วยข้อมูลจริง)

**วิธี (leave-one-out):** เอาประวัติรีวิวจริงของลูกค้า Amazon 1 คน → **ซ่อนสินค้าชิ้นล่าสุด 1 ชิ้น** → ใช้ที่เหลือเป็น "รสนิยม" ไปค้นหา → วัดว่าดึงชิ้นที่ซ่อนกลับมาใน top-k ได้ไหม (เหมือนถามว่า "ระบบทายของชิ้นต่อไปที่ลูกค้าจะซื้อได้ไหม")

**ผลจริง** (หมวด Office Products · 155 สินค้ารีวิวหนาแน่น · 300 ผู้ใช้):

| ตัวชี้วัด | ผล | เดามั่ว | ดีกว่ามั่ว |
|---|---|---|---|
| Recall@1 | 0.05 | 0.006 | 7.8x |
| Recall@10 | **0.23** | 0.065 | 3.5x |
| Recall@20 | 0.37 | 0.129 | 2.9x |

👉 อ่านผล: ให้เดา 10 อันดับแรก ระบบทายชิ้นที่ลูกค้าซื้อจริงถูก **~23%** (ดีกว่าเดามั่ว 3.5 เท่า)
👉 **จุดสอนสำคัญ (ซื่อสัตย์):** ค่านี้ไม่สูงลิ่ว เพราะ retriever เป็น **content-based** (ดูเนื้อหาสินค้า) แต่ "การทายชิ้นถัดไป" จริงๆ เป็นงาน **collaborative filtering** (ดูว่าคนคล้ายกันซื้ออะไร) — คนละงานกัน · แต่ยังพอมีสัญญาณเพราะ catalog เล็ก+หนาแน่น สินค้าออฟฟิศที่เนื้อหาคล้ายกันจึงจับได้บ้าง

> ข้อมูลสตรีมสดจาก Amazon Reviews 2023 · ปรับหมวด/จำนวนได้ในหัวไฟล์ (`CATEGORY`, `MAX_REVIEW_LINES`)

# 8. วิธีรัน + โครงสร้างไฟล์ + สถานะ

## วิธีรัน
```bash
python cli.py                 # คุยผ่านหน้าจอ terminal
python cli.py --debug         # + โชว์ความคิดของ agent (action/โน้ต/คะแนน) ทุกรอบ

python -m eval.test_dialogs   # ทดสอบพฤติกรรม 5 สถานการณ์
python -m eval.eval_products  # วัดการค้นหา + การกรองงบ
python -m eval.eval_system    # วัดความเร็ว + ความนิ่ง
python -m eval.eval_simulator # จำลองลูกค้าคุยหลายรอบ (Success@t + Avg turns)
python -m eval.eval_amazon_loo # (มาตรฐาน) leave-one-out Recall@k จากรีวิวจริง
```
